# Current implementation state

[← Documentation map](TOC.md)

This page is a compact description of the implementation that exists in the current source tree. It is intentionally not a roadmap and not a chronology. Historical designs that have been superseded are called out only where doing so prevents an operator or contributor from using a retired interface.

## Management boundary

`./local-ai` is the only supported management interface. The current public command families are:

- installation and lifecycle: `install`, `start`, `stop`;
- operational inspection: `status`, `doctor`, `inventory rescan`;
- version maintenance: `upgrade`, `upgrade policy`, `upgrade adopt`;
- recovery: `backup`, `restore plan`, `restore drill`, `restore apply`, `restore resume`;
- shell integration: `completion bash`, `completion zsh`, `completion install`, `completion status`.

Implementation lives under `commands/`, with disaster-recovery implementation under `commands/recovery/`. Stack-owned scripts remain implementation details behind the management boundary.

## Stack and component model

The platform contains eight independently owned stacks, numbered 0 through 7. Stack0 is the common foundation. Stack6 and Stack7 require Stack3. Stack2 capabilities are optional to the AI consumers.

Operational component topology is manifest-driven. Each stack `manifest.json` declares physical ownership in `owns[]` and operational semantics in `components[]`. Components are classified as `versioned`, `local`, `helper` or `platform`. Compose binds those semantic components to concrete services but is not a second component catalog.

`inventory rescan` produces a diagnostic topology snapshot and source fingerprint. That snapshot is history/evidence only: normal management reads compile the current manifests directly and do not depend on a previously generated catalog.

## Source, runtime and version authority

Git contains the bootstrap/source baseline. Mutable installation state is installation-owned and lives outside the source checkout. The protected operational `.env` is not silently regenerated by PREPARE.

For versioned components, the operational model distinguishes:

- **desired** — installation-owned exact version intent, with exact Compose source used only as bootstrap fallback before adoption;
- **deployed** — last confirmed deployment/adoption baseline;
- **actual** — concrete runtime identity;
- **available** — registry discovery only;
- **drift** — disagreement between desired and actual identity.

The normal human interface deliberately simplifies this model: `status` answers whether stacks are operational/coherent, while `upgrade` is the normal version-maintenance view. Registry discovery never becomes desired state or operator consent.

Existing installations that predate operational version authority use `upgrade adopt`. Adoption records already-running identities and is intentionally non-disruptive.

## Upgrade execution

`./local-ai upgrade` discovers installed and available versions. A target must be selected explicitly before `upgrade --yes` can mutate runtime. Compatibility policy and project qualification are separate gates.

A normally selectable component has a qualified guarded executor. An inventory-only component remains non-selectable unless an administrator explicitly uses `--force` and a deterministic mutation recipe already exists. Force bypasses project qualification only; it does not bypass immutable target validation, compatibility policy, stale-plan checks, recovery requirements, READY/VERIFY or dependent-consumer checks.

Remote registry failures are fail-closed. Rate limiting, authentication/authorization failure or indeterminate latest-only ordering produce unknown availability rather than a false `current` result.

## Lifecycle

The installation lifecycle remains:

`PREPARE → DEPLOY → READY → RECONCILE → VERIFY`

A stack `.lock` means PREPARED only. Selective `stop` refuses to break an active required consumer. Selective `start` does not invent or automatically start a missing provider.

## Shell completion

TAB completion is manifest-aware and source-local. Candidate calculation does not query Docker or registries. Bash and Zsh adapters can be generated without mutation, or installed persistently with `./local-ai completion install`. The installer detects Bash/Zsh, uses a system target for root and a per-user target otherwise, is idempotent and does not rewrite shell startup files.

## Disaster recovery

Recovery remains manifest-driven. The protected operational `.env` is a sensitive global artifact. Stack0 PKI, Stack3 logical database state, Stack4 native Gitea state and Stack7 Open WebUI data are managed recovery artifacts. Stack6 runtime is reconstructable; its durable user-memory contract is Git-backed.

Backup destination validation rejects destinations equal to, inside, or ancestors of protected source/runtime roots. Restore planning, drills, clean-target apply and resumable recovery remain explicit operations rather than implicit lifecycle side effects.

## Retired implementation surfaces

The following are intentionally **not** part of the current architecture:

- separate top-level `internal/`, `installer/` and `bkp-dr/` implementation roots;
- the static `commands/upgrade-components.json` component catalog;
- Git/Compose as ongoing operational version authority after installation adoption;
- `tracked-compose-pin` as a generic reason to block upgrades;
- registry discovery as implicit selection or permission to upgrade;
- direct stack scripts, Compose commands or Python modules as supported external management APIs.

Historical ADRs, restore compatibility code and tests may mention a retired path when explaining a migration or proving backward recovery. Such references are historical evidence, not a reintroduction of the retired interface.

## Evidence boundary

Repository tests prove deterministic source contracts. Runtime qualification is required for behaviours that depend on a real Docker engine, registry or application. The canonical full repository gate is documented in [developer testing](devel-docs/testing.md), and behavioural mappings live in [OpenSpec traceability](devel-docs/openspec/traceability.md).
