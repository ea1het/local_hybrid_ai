# AI-assisted maintenance context

> **Agent-oriented reference — not an operator guide.**

[← Documentation map](TOC.md) · [Current state](current-state.md) · [Management plane](architecture/management-plane.md)

This compact reference supports AI-assisted maintenance and contributor continuity. It is not an alternative source of truth. A maintenance agent or contributor derives current behaviour from the root [README](../README.md), [current implementation state](current-state.md), affected manifests/stack documentation, ADR/SDR/OpenSpec contracts and tests. [Pending work](pending.md) contains only active or intentionally deferred work.

## Platform invariants

- The platform consists of eight atomic stacks rather than one monolithic Compose project.
- Every application stack requires Stack0; Stack6 and Stack7 additionally require Stack3.
- Stack2 web capabilities are optional to Stack6/7. Optional relationships do not become hard lifecycle dependencies.
- `.lock` means PREPARED only.
- Lifecycle is `PREPARE → DEPLOY → READY → RECONCILE → VERIFY`; restart-causing reconciliation returns through READY.
- The operational root `.env` is protected, ignored by Git and not silently regenerated by normal PREPARE.
- Runtime ownership and component semantics are declared in manifests. `owns[]` is physical ownership; `components[]` is operational component topology.
- Component classes are `versioned`, `local`, `helper` and `platform`.
- Normal management compiles current manifests directly. `inventory rescan` creates diagnostic history, not authority.
- General manifest graph/capability semantics and Recovery-specific manifest validation remain distinct responsibilities.
- Common lifecycle and DR orchestration stay generic only where behaviour is genuinely common; stack-specific safety behaviour remains explicit rather than being hidden behind abstraction for its own sake.

## Management and version invariants

`./local-ai` is the sole supported management/automation boundary. `src/local_ai_cli/`, `src/local_ai_cli/recovery/`, stack scripts and Compose files are private implementation surfaces.

The management plane separates lifecycle, upgrade and Recovery responsibilities. Upgrade keeps command orchestration, selection/stale-plan policy, inventory/catalog/plan/cache state, runtime observation, OCI registry handling and guarded mutation distinct. Recovery keeps planning/orchestration separate from destination/runtime-source preflight and from mutating backup/restore phases. These boundaries support auditability; they are not public Python APIs.

The current source tree has no separate top-level `internal/`, `installer/` or `bkp-dr/` implementation roots and no static `src/local_ai_cli/upgrade-components.json` catalog. Historical restore compatibility may recognize old layouts without making them current APIs.

Git/Compose is the bootstrap source baseline. After adoption, version intent is installation-owned. The following facts remain separate:

- desired: installation-owned exact intent (Compose fallback only before adoption);
- deployed: last confirmed deployment/adoption baseline;
- actual: concrete runtime identity;
- available: registry discovery only;
- drift: desired and actual disagree.

`status` is the stack-operational view; `upgrade` is the normal human version view. Registry discovery never selects or authorizes an upgrade. Registry 429/401/403 or otherwise indeterminate discovery remains unknown/fail-closed.

Public stack selectors are numeric `0` through `7`. Internal identities such as `stack7` remain machine/manifests data and are not alternate public selectors.

`upgrade adopt` records existing runtime identities without pulling or restarting. Normal selection requires a qualified executor. `--force` is only an explicit administrator qualification bypass when a deterministic mutation recipe exists; it does not bypass target, digest, policy, stale-plan, recovery, READY, VERIFY or consumer gates. Compatibility seams used by status/tests remain intentional unless a concrete functional change removes their consumers.

## Security invariants

- Hermes has no Docker socket; execution is isolated in its SSH sandbox.
- The sandbox uses a private execution network and is not attached to the shared `redlocal` application network.
- Applications use dedicated LiteLLM virtual credentials rather than the administrative master key.
- Internal services normally communicate over Stack0-owned `redlocal`; host exposure is explicit.
- Open WebUI keeps model access control enabled and grants `basic_autorouter` explicit public read access instead of bypassing access control.
- Security rationale belongs in [SDRs](devel-docs/sdr/README.md).

## Stack6 execution and continuity

Hermes depends on Stack0 and Stack3; Stack2 capabilities remain optional. PREPARE validates prerequisites before mutation, prepares persistent paths/configuration and SSH isolation, initializes generation/state fail-closed, reconciles Git-backed memory and maintenance sidecars, then capability reconciliation converges runtime policy.

Hermes native Cron is the agentic deferred-work mechanism because each scheduled execution starts a fresh agent session. Scheduled prompts therefore carry sufficient context to stand alone. Deterministic Git-memory synchronization and sandbox housekeeping remain sidecars rather than agentic Cron work.

Durable memory is the Git-backed `MEMORY.md` and `USER.md` contract. Memory synchronization never force-pushes; divergence fails closed, remote-ahead state may fast-forward only when the local memory worktree is clean, and a dedicated SSH identity is used when configured.

## Persistence and disaster recovery

Stack0 PKI, Stack3 logical LiteLLM database, Stack4 Gitea native state and Stack7 Open WebUI data are managed recovery artifacts. Stack6 runtime is reconstructable; Git-backed `MEMORY.md` and `USER.md` are its durable user-memory contract. The protected operational `.env` is a sensitive global recovery artifact.

Recovery follows `Plan → Preflight → Backup/Recovery Point → Validate → Stage → Managed → Live → Resume → READY/VERIFY`. Planning and preflight are read-only boundaries. Backup publication and restore mutation are explicit phases. Backup destination validation rejects equal, descendant and ancestor overlap with protected source/runtime paths after normalization. Qualified capability evidence is summarized in [DR status](dr/status.md).

## Shell completion

Bash/Zsh completion is part of the current CLI. Candidate calculation is source-local and manifest-aware; it does not inspect Docker or registries. `completion install` performs the explicit persistent write, detects Bash/Zsh, distinguishes system/user targets, is idempotent and does not rewrite shell startup files.

## Change discipline

A maintenance change first identifies the owning subsystem and then inspects its manifest, Compose binding, implementation, decisions and behavioural specifications. The preferred change is the smallest ownership-correct change that preserves explicit safety boundaries. Generic `utils`, factories, adapter registries or shared shell frameworks are not introduced merely to reduce textual duplication.

Deterministic repository tests provide source evidence. Runtime qualification is requested only where source evidence cannot prove behaviour. Deployment/runtime success is never inferred from source-only evidence. Completed work belongs in Git history and durable contracts, not in [pending.md](pending.md).
