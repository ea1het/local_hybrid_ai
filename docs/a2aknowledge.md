# AI-assisted maintenance context

This is compact maintenance context for contributors and automation, not an alternative source of truth. Read the root [README](../README.md), [current implementation state](current-state.md), [pending work](pending.md), the affected stack manifest/README and relevant ADR/SDR/OpenSpec before changing behaviour.

## Platform invariants

- The platform is eight atomic stacks, not one monolithic Compose project.
- Every application stack requires Stack0; Stack6 and Stack7 additionally require Stack3.
- Stack2 web capabilities are optional to Stack6/7. Optional relationships must not become hard lifecycle dependencies.
- `.lock` means PREPARED only.
- Lifecycle is `PREPARE → DEPLOY → READY → RECONCILE → VERIFY`; restart-causing reconciliation returns through READY.
- The operational root `.env` is protected, ignored by Git and not silently regenerated by normal PREPARE.
- Runtime ownership and component semantics are declared in manifests. `owns[]` is physical ownership; `components[]` is operational component topology.
- Component classes are `versioned`, `local`, `helper` and `platform`.
- Normal management compiles current manifests directly. `inventory rescan` creates diagnostic history, not authority.
- Common lifecycle and DR orchestration stay generic; stack-specific behaviour belongs in manifests, adapters or stack-owned scripts.

## Management and version invariants

`./local-ai` is the sole supported management/automation boundary. `commands/`, `commands/recovery/`, stack scripts and Compose files are private implementation surfaces.

The current source tree has no separate top-level `internal/`, `installer/` or `bkp-dr/` implementation roots and no static `commands/upgrade-components.json` catalog. Historical restore compatibility may recognize old layouts without making them current APIs.

Git/Compose is the bootstrap source baseline. After adoption, version intent is installation-owned. Keep these facts separate:

- desired: installation-owned exact intent (Compose fallback only before adoption);
- deployed: last confirmed deployment/adoption baseline;
- actual: concrete runtime identity;
- available: registry discovery only;
- drift: desired and actual disagree.

`status` is the stack-operational view; `upgrade` is the normal human version view. Registry discovery never selects or authorizes an upgrade. Registry 429/401/403 or otherwise indeterminate discovery remains unknown/fail-closed.

`upgrade adopt` records existing runtime identities without pulling or restarting. Normal selection requires a qualified executor. `--force` is only an explicit administrator qualification bypass when a deterministic mutation recipe exists; it does not bypass target, digest, policy, stale-plan, recovery, READY, VERIFY or consumer gates.

## Security invariants

- Hermes has no Docker socket; execution is isolated in its sandbox.
- Applications use dedicated LiteLLM virtual credentials rather than the administrative master key.
- Internal services normally communicate over Stack0-owned `redlocal`; host exposure is explicit.
- Open WebUI keeps model access control enabled and grants `basic_autorouter` explicit public read access instead of bypassing access control.
- Security rationale belongs in [SDRs](devel-docs/sdr/README.md).

## Persistence and disaster recovery

Stack0 PKI, Stack3 logical LiteLLM database, Stack4 Gitea native state and Stack7 Open WebUI data are managed recovery artifacts. Stack6 runtime is reconstructable; Git-backed `MEMORY.md` and `USER.md` are its durable user-memory contract. The protected operational `.env` is a sensitive global recovery artifact.

Backup destination validation rejects equal, descendant and ancestor overlap with protected source/runtime paths after normalization. Qualified capability evidence is summarized in [DR status](dr/status.md).

## Shell completion

Bash/Zsh completion is part of the current CLI. Candidate calculation is source-local and manifest-aware; it does not inspect Docker or registries. `completion install` performs the explicit persistent write, detects Bash/Zsh, distinguishes system/user targets, is idempotent and does not rewrite shell startup files.

## Change discipline

Identify the owning subsystem first, then inspect its manifest, Compose binding, implementation, decisions and behavioural specifications. Prefer the smallest ownership-correct change. Run deterministic repository tests and request runtime qualification only where source evidence cannot prove the behaviour.

Deployment/runtime success must never be inferred from source-only evidence. Completed work belongs in Git history and durable contracts, not in [pending.md](pending.md).
