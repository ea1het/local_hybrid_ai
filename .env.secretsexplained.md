# Secrets explained — `.env` and runtime identities

This document explains **where every secret in the central `.env` comes from, who is allowed to generate it, what kind of secret it is, where it is stored, what consumes it, and whether it may be rotated**.

The central `.env.template` remains the variable contract. It should say *which variables exist* and whether they are sensitive. This document explains *how sensitive values are provisioned and managed*.

> Never copy real secret values into Git, issues, pull requests, chat transcripts, screenshots, CI logs or documentation. Commands below are generation recipes; their output belongs only in the protected operational environment or the documented runtime secret path.

## 1. Secret classes used by this project

The platform deliberately distinguishes several secret origins.

| Class | Meaning | Typical examples |
|---|---|---|
| **operator-generated** | You generate a cryptographically random value locally during bootstrap. | SearXNG secret, application database passwords, LiteLLM master/salt, Hermes API signing secret |
| **application-generated** | The owning application has a native secret generator and that generator should be preferred. | Gitea `INTERNAL_TOKEN`, Gitea `JWT_SECRET` |
| **service-issued credential** | Another running system creates a credential granting access to that system. Do not replace it with an arbitrary random string. | LiteLLM virtual keys used by Hermes |
| **external-provider credential** | A third-party service/account issues the credential. | Telegram BotFather token, optional Buzz credentials |
| **runtime-generated identity** | A stack script generates the identity outside `.env`, stores it in `/opt/docker/runtime`, and preserves it. | Stack2/Stack3 PostgreSQL admin passwords, Stack6 sandbox SSH keys |
| **operator-provisioned runtime identity** | The secret deliberately lives outside `.env`, but the operator must create/authorize it. | Hermes memory-sync SSH identity for Gitea |
| **derived secret** | The stored value is derived from a human secret and is not the plaintext secret itself. | Hermes dashboard scrypt password hash |

A secret being self-generatable does **not** mean it is disposable. Many generated values become persistent identities once data has been encrypted, tokens have been issued, or peers have trusted them.

## 2. Safe local generators

For opaque random values created by the operator, these are reasonable bootstrap primitives:

```bash
# 32 random bytes represented as 64 hexadecimal characters
openssl rand -hex 32

# 32 random bytes represented as base64
openssl rand -base64 32

# OpenAI-style opaque token when a component expects/prefer an sk- prefix
printf 'sk-%s\n' "$(openssl rand -hex 32)"
```

Do not use short memorable strings for infrastructure secrets. Generate them once, store them only where the contract says, back up the operational secret store appropriately, and preserve them across reinstall/upgrade.

## 3. Stack2 — SearXNG + Firecrawl

### `SEARXNG_SECRET`

- **Type:** application/session secret.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational root `.env`.
- **Consumed by:** SearXNG.
- **Lifecycle:** generate once and preserve.
- **Rotation:** possible only as an intentional application-secret rotation. Existing sessions/signatures may be invalidated; never rotate during routine PREPARE or installer convergence.

### `REDIS_PASSWORD`

- **Type:** internal service password.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** Firecrawl and `firecrawl-redis`.
- **Lifecycle:** generated once/persistent.
- **Rotation:** coordinated change across Redis and every client; not a routine maintenance operation.

### `RABBITMQ_PASSWORD`

- **Type:** internal message-broker account password.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** RabbitMQ and Firecrawl/NuQ.
- **Related non-secret identity:** `RABBITMQ_USER`.
- **Lifecycle:** generated once/persistent.
- **Rotation:** coordinated broker/client credential change.

### `FIRECRAWL_DB_PASSWORD`

- **Type:** dedicated Firecrawl application database-role password.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** `firecrawl-api` and Stack2 PostgreSQL role provisioning/bootstrap.
- **Related non-secret identities:** `FIRECRAWL_DB_USER=firecrawl`, `FIRECRAWL_DB_NAME=postgres`.
- **Privileges:** application role only: no superuser, no CREATEDB, no CREATEROLE, no replication, no BYPASSRLS. It receives only the database/schema/object privileges required to use NUQ.
- **Lifecycle:** generated once/persistent database credential.
- **Rotation:** change the actual PostgreSQL role credential and the Firecrawl consumer together. Editing `.env` alone is not a safe rotation procedure.

Firecrawl deliberately **does not** use the PostgreSQL `postgres` administrative role during normal operation.

### Stack2 PostgreSQL administrative password — intentionally **not** in `.env`

Path:

```text
${BASE_PATH}/service_-_firecrawl-postgres/secret/postgres_admin_password
```

- **Type:** PostgreSQL cluster administrative/bootstrap password for role `postgres`.
- **Origin on a fresh runtime:** Stack2 `01-prepare.sh`.
- **Generator on a fresh runtime:** `openssl rand -hex 32`.
- **Stored in:** runtime file, `root:root 0600`.
- **Consumed by:** the PostgreSQL container through `POSTGRES_PASSWORD_FILE` during initial cluster bootstrap; it is not an application credential.
- **Ownership:** `postgres` remains the administrative/owner role for the NUQ schema, `pg_cron`, `pgcrypto` and upstream bootstrap objects.
- **Lifecycle:** generated once and preserved.
- **Why outside `.env`:** the administrative credential is Stack2-owned runtime state and is not needed by normal application consumers.
- **Rotation:** explicit PostgreSQL-administration procedure only. Never rotate during routine PREPARE/convergence.

For an **existing deployment** created before this separation, the original `POSTGRES_PASSWORD` in `.env` is already the live password of role `postgres`. `03-migrate-postgres-app-role.sh` therefore **adopts that exact existing value once** into the runtime secret file rather than generating a different password. It then creates/reconciles the dedicated Firecrawl application role and validates a rollback-only CRUD probe before Compose is changed to use the new application identity. After migration and runtime validation, the legacy Stack2 `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` entries should be removed from the operational `.env`.

The migration does not alter PGDATA, does not change NUQ/cron ownership, does not rotate the existing `postgres` password, and does not restart containers by itself.

## 4. Stack3 — LiteLLM + dedicated PostgreSQL

### `LITELLM_MASTER_KEY`

- **Type:** LiteLLM administrative/master API credential.
- **Origin:** operator-generated during initial LiteLLM bootstrap.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `printf 'sk-%s\n' "$(openssl rand -hex 32)"`.
- **Stored in:** operational `.env`.
- **Consumed by:** LiteLLM proxy administrative/authentication layer.
- **Lifecycle:** persistent master credential.
- **Rotation:** high-impact administrative rotation. Do not rotate implicitly and do not confuse it with per-client LiteLLM virtual keys.

### `LITELLM_SALT_KEY`

- **Type:** persistent encryption salt/key material used by LiteLLM for encrypted database-backed values.
- **Origin:** operator-generated during first installation.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** LiteLLM.
- **Lifecycle:** **persistent cryptographic identity**.
- **Rotation:** **do not rotate casually**. Once LiteLLM has encrypted state in PostgreSQL, changing this value can make stored encrypted values unusable. Restoration of an existing LiteLLM database must restore the matching salt key as well.

### `UI_PASSWORD`

- **Type:** human administrator password for the LiteLLM UI.
- **Origin:** operator-selected/generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** use a password-manager-generated high-entropy password rather than a manually memorable infrastructure password.
- **Stored in:** operational `.env`.
- **Consumed by:** LiteLLM UI authentication.
- **Related non-secret identity:** `UI_USERNAME`.
- **Rotation:** normal administrative password rotation is possible, but it should be intentional and validated against the running UI.

### `LITELLM_DB_PASSWORD`

- **Type:** application database-role password for the dedicated LiteLLM PostgreSQL database.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** LiteLLM and Stack3 PostgreSQL role provisioning.
- **Related non-secret identities:** `LITELLM_DB_USER`, `LITELLM_DB_NAME`.
- **Lifecycle:** persistent database credential.
- **Rotation:** must change both the actual PostgreSQL role credential and LiteLLM configuration consistently. Do not rotate by editing `.env` alone.

### PostgreSQL administrative password — intentionally **not** in `.env`

Path:

```text
${BASE_PATH}/service_-_litellm-postgres/secret/postgres_admin_password
```

- **Type:** PostgreSQL cluster administrative password.
- **Origin:** **our Stack3 `01-prepare.sh`**, not LiteLLM and not a LiteLLM package behavior.
- **Generator:** `openssl rand -hex 32`.
- **Can you generate it yourself?** Normally you should let Stack3 generate it on a fresh runtime. For an existing deployment, preserve the existing file.
- **Stored in:** runtime file, `root:root 0600`.
- **Lifecycle:** generated once and preserved.
- **Why outside `.env`:** it is a Stack3-owned host/runtime identity and does not need to be part of the shared environment contract.
- **Rotation:** explicit database-administration procedure only.

## 5. LiteLLM credentials consumed by Hermes

These two values look like arbitrary API secrets, but in the architecture they are **service-issued credentials**. They represent permissions granted by Stack3/LiteLLM to Stack6/Hermes.

### `LITELLM_API_KEY`

- **Type:** dedicated LiteLLM client/virtual key for Hermes model inference.
- **Origin:** **created/issued by LiteLLM**, not invented independently in `.env`.
- **Can you generate it yourself with `openssl rand`?** No, not as a working authorization credential. A random string is not registered with LiteLLM.
- **Provisioning model:** use LiteLLM's key-management/admin surface to create a dedicated key with the intended model/budget/policy scope, then copy the issued key into `.env`.
- **Stored in:** operational `.env`.
- **Consumed by:** Hermes when calling `LITELLM_BASE_URL`.
- **Lifecycle:** persistent service-issued credential until intentionally revoked/replaced.
- **Rotation:** issue a replacement in LiteLLM, update Hermes, validate, then revoke the old key.

### `LITELLM_MCP_API_KEY`

- **Type:** dedicated LiteLLM client/virtual key for Hermes MCP access.
- **Origin:** **created/issued by LiteLLM**.
- **Can you generate it yourself with `openssl rand`?** No, for the same reason as `LITELLM_API_KEY`.
- **Provisioning model:** create a dedicated credential in LiteLLM for the MCP policy/scope, then store the returned key in `.env`.
- **Stored in:** operational `.env`.
- **Consumed by:** Hermes at `LITELLM_MCP_URL`.
- **Lifecycle:** persistent service-issued credential.
- **Design rule:** keep inference and MCP credentials separate so compromise/revocation can be scoped.

## 6. Stack4 — Gitea + Actions runner

### `GITEA_INTERNAL_TOKEN`

- **Type:** Gitea internal API/authentication token.
- **Origin:** Gitea application-generated secret.
- **Can you generate it yourself?** Yes, but use **Gitea's own generator**, not a generic random format.
- **Preferred generation:** run the pinned Gitea image's `gitea generate secret INTERNAL_TOKEN` command and capture its output directly into the protected `.env`.
- **Stored in:** operational `.env` and rendered into Gitea's managed configuration.
- **Lifecycle:** persistent secret; preserve existing deployments.
- **Rotation:** do not rotate implicitly. Internal Gitea operations depend on it.

Example pattern (replace the image with the exact pin from `.env.template`):

```bash
docker run --rm docker.gitea.com/gitea:1.27.1-rootless \
  gitea generate secret INTERNAL_TOKEN
```

### `GITEA_JWT_SECRET`

- **Type:** Gitea JWT signing/authentication secret used by configured JWT features.
- **Origin:** Gitea application-generated secret.
- **Can you generate it yourself?** Yes, using Gitea's native generator.
- **Preferred generation:** `gitea generate secret JWT_SECRET` using the pinned image.
- **Stored in:** operational `.env` and rendered Gitea configuration.
- **Lifecycle:** persistent signing identity.
- **Rotation:** existing signed tokens may become invalid. Never rotate as part of PREPARE/upgrade.

Example:

```bash
docker run --rm docker.gitea.com/gitea:1.27.1-rootless \
  gitea generate secret JWT_SECRET
```

### `GITEA_ADMIN_PASSWORD`

- **Type:** human bootstrap administrator password.
- **Origin:** operator-selected/generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** password-manager-generated strong password.
- **Stored in:** operational `.env` during bootstrap/configuration.
- **Consumed by:** Stack4 admin-user creation/validation.
- **Related non-secret identity:** `GITEA_ADMIN_USERNAME`, `GITEA_ADMIN_EMAIL`.
- **Rotation:** normal Gitea account password rotation after bootstrap is possible. Do not assume changing `.env` automatically changes an already-created Gitea user's password unless the owning lifecycle explicitly does so.

### Gitea runner registration token — intentionally **not** in `.env`

Path:

```text
${BASE_PATH}/service_-_gitea-runner/secret/registration-token
```

- **Type:** persistent runner registration/bootstrap secret.
- **Origin:** Stack4 PREPARE on a fresh runtime, or one-time adoption from the former legacy `.env` variable if present.
- **Generator used by current Stack4:** `openssl rand -hex 24`.
- **Stored in:** runtime secret file with restricted permissions.
- **Lifecycle:** generated/adopted once and preserved.
- **Why outside `.env`:** runner identity is Stack4-owned runtime state, not shared platform configuration.

## 7. Stack6 — Hermes application secrets

### `TELEGRAM_BOT_TOKEN`

- **Type:** external-provider bot credential.
- **Origin:** Telegram **BotFather**.
- **Can you generate it yourself locally?** No. Telegram issues it when the bot is created/managed.
- **Stored in:** operational `.env` when Telegram integration is enabled; may be empty when disabled.
- **Consumed by:** Hermes Telegram integration.
- **Rotation/revocation:** performed through BotFather, then update the local `.env` and restart/reconcile as required.

### `BUZZ_PRIVATE_KEY`

- **Type:** optional Buzz cryptographic identity/private key.
- **Origin:** the Buzz integration/provisioning workflow, external to the current repository.
- **Can you generate it yourself?** Only according to the Buzz protocol/tooling expected by Hermes. The current repository does not define a compatible key generator, so do not substitute an arbitrary value.
- **Stored in:** operational `.env` only when Buzz is enabled.
- **Lifecycle:** external/provider-specific persistent secret.

### `BUZZ_AUTH_TAG`

- **Type:** optional Buzz authentication material.
- **Origin:** Buzz integration/provisioning workflow.
- **Can you generate it yourself?** Not from repository rules alone; use the Buzz system's expected procedure.
- **Stored in:** operational `.env` when required.
- **Lifecycle:** provider-specific.

`BUZZ_RELAY_URL` and `BUZZ_CLI_PATH` are configuration, not secrets.

### `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH`

- **Type:** **derived secret**: scrypt password hash, not the dashboard plaintext password.
- **Origin:** generated from the operator's chosen dashboard password using Hermes' own hashing helper.
- **Can you generate it yourself?** Yes.
- **Preferred generation:** use the exact Hermes version/runtime implementation so the format is guaranteed compatible.

Hermes upstream documents the generator conceptually as:

```bash
python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"
```

For this project, prefer running that helper in a controlled environment matching the pinned Hermes release rather than installing an unrelated copy on the host. Do not commit or log the plaintext password.

- **Stored in:** operational `.env`.
- **Consumed by:** Hermes dashboard basic-auth provider.
- **Lifecycle:** persistent until the operator changes the dashboard password.
- **Rotation:** generate a new hash from a new password, update `.env`, recreate/restart Hermes deliberately, validate login.

### `HERMES_DASHBOARD_BASIC_AUTH_SECRET`

- **Type:** HMAC/session-token signing secret.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** at least 32 random bytes, for example `openssl rand -base64 32` or `openssl rand -hex 32`.
- **Stored in:** operational `.env`.
- **Consumed by:** Hermes dashboard authentication.
- **Why persistent:** keeping an explicit stable signing secret allows sessions to survive process restarts; a per-process random secret would invalidate sessions on restart.
- **Rotation:** invalidates existing dashboard sessions/tokens; do only intentionally.

### `API_SERVER_KEY`

- **Type:** Hermes Runs/API bearer/API credential.
- **Origin:** operator-generated.
- **Can you generate it yourself?** Yes.
- **Recommended bootstrap:** `printf 'sk-%s\n' "$(openssl rand -hex 32)"` or another high-entropy opaque token. The current Stack6 validation requires at least 8 characters; use substantially more.
- **Stored in:** operational `.env`.
- **Consumed by:** Hermes API server clients/authentication.
- **Lifecycle:** generated once/persistent until deliberate API-key rotation.

### `FIRECRAWL_API_KEY`

- **Type:** optional local Firecrawl authentication credential.
- **Current deployment:** intentionally empty because local Firecrawl authentication is disabled.
- **Origin if enabled in future:** must match the authentication mechanism configured on the Firecrawl provider.
- **Can you generate it yourself today?** Not meaningfully while auth is disabled. If auth is added later, define the provider-side issuance/validation contract first.
- **Stored in:** operational `.env` only when that future auth contract requires it.

## 8. Stack6 SSH identities — deliberately outside `.env`

The `.env` contains `TERMINAL_SSH_KEY`, but that variable is only the **path inside the Hermes container**. The private key bytes do not belong in `.env`.

### Hermes executor keypair

Runtime path:

```text
${BASE_PATH}/service_-_hermes/config/ssh/hermes_executor_ed25519
${BASE_PATH}/service_-_hermes/config/ssh/hermes_executor_ed25519.pub
```

- **Type:** Ed25519 client SSH identity for Hermes -> sandbox execution.
- **Origin:** Stack6 `01-prepare.sh`.
- **Generator:** `ssh-keygen -t ed25519` with no passphrase for this non-interactive bounded service identity.
- **Stored in:** Stack6 runtime config; private key mode `0600`.
- **Lifecycle:** generated once and preserved; PREPARE validates existing keypair consistency.
- **Rotation:** coordinated sandbox authorization change only.

### Sandbox SSH host key

Runtime path:

```text
${BASE_PATH}/service_-_hermes-sandbox/config/ssh-host/ssh_host_ed25519_key
${BASE_PATH}/service_-_hermes-sandbox/config/ssh-host/ssh_host_ed25519_key.pub
```

- **Type:** Ed25519 SSH server host identity.
- **Origin:** Stack6 `01-prepare.sh`.
- **Generator:** `ssh-keygen -t ed25519`.
- **Lifecycle:** persistent host identity.
- **Rotation:** changes the sandbox host fingerprint/trust relationship; do not rotate as routine cleanup.

### Hermes memory-sync SSH identity

Runtime directory:

```text
${BASE_PATH}/service_-_hermes-memory-sync/ssh/
├── id_ed25519
├── known_hosts
└── ssh_config
```

- **Type:** dedicated Git-over-SSH identity for the memory-sync sidecar -> Gitea.
- **Origin:** **operator-provisioned runtime identity**.
- **Current repository behavior:** `05-maintenance-sidecars.sh` deliberately **does not generate, copy or replace it**. It only verifies that the required files already exist.
- **Can you generate it yourself?** Yes, using `ssh-keygen -t ed25519`, but you must then authorize the public key in the correct Gitea account/repository context and build the expected `known_hosts`/`ssh_config` safely.
- **Why separate:** Hermes sandbox execution and Git-memory synchronization have different trust scopes and must not share one private key.
- **Rotation:** provision a replacement key, authorize it, validate Git access and only then retire the old key.

## 9. Stack0 PKI — secret identity outside `.env`

Stack0 owns the platform TLS PKI under the platform runtime. The private key is **not** an environment variable.

- **Type:** TLS private key + certificate identity.
- **Origin:** Stack0 PKI lifecycle (`pki.sh`).
- **Can you generate it yourself?** The owning Stack0 tooling should manage it so permissions/consumers remain coherent.
- **Lifecycle:** persistent identity; existing valid PKI is preserved.
- **Rotation:** use the explicit PKI renew/recreate lifecycle. Recreating a private key is materially different from renewing a certificate with the same key.
- **Rule:** never place the TLS private key in `.env` or Git.

## 10. What is sensitive even if it is not literally a password

Treat these as sensitive or security-relevant even when their names do not contain `PASSWORD`:

- `LITELLM_MASTER_KEY`
- `LITELLM_SALT_KEY`
- `GITEA_INTERNAL_TOKEN`
- `GITEA_JWT_SECRET`
- `LITELLM_API_KEY`
- `LITELLM_MCP_API_KEY`
- `TELEGRAM_BOT_TOKEN`
- `BUZZ_PRIVATE_KEY`
- `BUZZ_AUTH_TAG`
- `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH`
- `HERMES_DASHBOARD_BASIC_AUTH_SECRET`
- `API_SERVER_KEY`
- any future non-empty `FIRECRAWL_API_KEY`
- TLS/SSH private key material in runtime
- runner registration secret
- Stack2 PostgreSQL administrative secret
- Stack3 PostgreSQL administrative secret

A password hash is still sensitive authentication material. An encryption salt/key such as `LITELLM_SALT_KEY` is also part of recoverability, not merely authentication.

## 11. Bootstrap checklist for a new installation

Before running the common installer on a fresh host:

1. Copy `.env.template` to the protected operational `.env`.
2. Set ownership/mode to `root:root 0600`.
3. Generate all **operator-generated** secrets locally, including application database-role passwords such as `FIRECRAWL_DB_PASSWORD` and `LITELLM_DB_PASSWORD`.
4. Generate Gitea internal/JWT secrets with the pinned Gitea application's native generator.
5. Bootstrap Stack3/LiteLLM before attempting to populate Hermes client keys that must be **issued by LiteLLM**.
6. Create/obtain external-provider credentials only for integrations that will actually be enabled.
7. Allow stack-owned PREPARE scripts to generate the runtime identities they explicitly own (for example Stack2/Stack3 PostgreSQL admin secrets and Stack6 sandbox SSH identities).
8. Provision operator-owned runtime credentials that PREPARE intentionally refuses to invent (currently the memory-sync SSH identity).
9. Never replace an existing deployment's persistent secret with a newly generated one merely because a placeholder exists in `.env.template`.

The distinction between **fresh install** and **restore/existing deployment** is critical. On a restore, recover the original persistent secrets that belong to the recovered databases/identities whenever possible.

## 12. Rotation rule

Do not treat secret rotation as a text-editing operation.

A proper rotation asks:

1. Who is the issuer/authority for this credential?
2. Which live service stores or validates it?
3. Which consumers must be updated?
4. Can old and new credentials overlap temporarily?
5. Does rotation invalidate encrypted state, sessions, JWTs, SSH trust or database access?
6. What is the rollback secret and where is it backed up?

If a secret is marked **persistent identity**, the safe default is preservation, not regeneration.

## 13. Adding secrets for future stacks (including Open WebUI)

When a new stack introduces a secret, update both `.env.template` and this document in the same change. Classify the secret before implementation:

- operator-generated;
- application-generated;
- service-issued;
- external-provider-issued;
- runtime-generated;
- operator-provisioned runtime identity;
- derived secret.

For each new secret document:

- variable/file name;
- owner stack;
- issuer/generator;
- exact storage location;
- consumers;
- minimum format/entropy requirements when known;
- fresh-install bootstrap procedure;
- restore procedure;
- rotation effect;
- whether an empty value means disabled;
- whether the secret belongs in `.env` at all.

For PostgreSQL-backed stacks, the default project pattern is now explicit: keep `postgres` as the stack-local administrative/bootstrap role with its password in a stack-owned runtime secret file, and give the application a separate non-admin role/password. Do not share one PostgreSQL admin credential across stacks.

Do **not** add a secret to the shared `.env` merely because passing environment variables is convenient. Stack-owned secrets that do not need to be shared should prefer an appropriately permissioned runtime secret file.
